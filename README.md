# buzz-host

Self-hosted provider for Buzz **remote agents**: the same contract Builderlab
uses, so agents run on your own server and keep answering while your laptop is
closed. You create and edit them from Buzz on any device.

```
Buzz (laptop) ── plugins (Remote Agents, Viewport, Hive Watch) ── wss://omarchy.<tailnet>:8447 (tailscale serve)
                                                   │
                                     buzz-host.mjs (127.0.0.1:8457, systemd --user)
                                                   │ per agent
                          buzz-agent@<pubkey>.service → agent-run → buzz-acp
                                                   │ ACP (via acp-v1-shim)
                                   claude-agent-acp | codex-acp | hermes-acp | agy acp
```

| `server/com.buzz-host.server.plist` | `~/Library/LaunchAgents/` (macOS) | buzz-host itself on macOS, filled in by `deploy.sh --local` |

Server-only state: `~/.config/buzz-host/config.json` (allowed Tailscale logins,
communities), `~/.local/share/buzz-host/agents/<pubkey>/` (key, auth.json,
instructions.md, runtime.env, meta.json; mode 0600), work dirs in `~/buzz-agents/<pubkey>`.
Binaries `buzz-acp` and `buzz` in `~/.local/lib/buzz-host/bin/` come from the
block/buzz desktop amd64 deb; adapters are npm packages in `~/.local/lib/buzz-host/npm/`.

## Security

- Listens on 127.0.0.1 only; reachable through `tailscale serve --https=8447`.
- Requests must carry a `Tailscale-User-Login` listed in `allowLogins` (tailscale
  serve sets it; tagged devices have none) and, if sent, an allowed Origin.
- A second listener (`guestPort`, default 8467) never trusts that header: every
  socket sends an access token in its first `auth` call (never in the URL).
  Guest tokens (`bhg_…`) are scoped, sandboxed friend accounts. Admin tokens
  (`bha_…`) give the owner full access from devices that are not on the
  tailnet, behind server-only Tailscale Funnel, zrok or any `wss://` proxy:
  `buzz-host tokens create-admin --label "My laptop" [--url wss://…]` prints the
  token and a 1-paste `wss://…#token=bha_…` pairing URL once. Tokens are stored
  only as SHA-256 hashes; `buzz-host tokens list` shows each one's role, and
  `buzz-host tokens revoke <tok_…>` cuts its connections within about 15 seconds.
  (`buzz-host-tokens <command>` is a compatibility shim for the same code.)
- `allowLogins` is optional. Leave it out (or empty) on a token-only host: the
  `Tailscale-User-Login` listener does not start at all.
- Agents only answer their owner by default (`BUZZ_ACP_RESPOND_TO=owner-only`).
- Sandboxed (Docker) agents run on their own bridge network `buzz-sandbox`
  (`buzzsbx0`, 172.30.0.0/24, no container-to-container traffic). A root
  nftables table (`server/sandbox/firewall/`) drops everything from that bridge
  to this host and to RFC1918, the tailnet (100.64/10), link-local, loopback,
  multicast and IPv6. Public internet still works, including the relay through
  its Funnel name. Install it once with `sudo server/sandbox/install-firewall.sh`
  (`--remove` to uninstall). `docker-run` refuses to start a sandboxed agent
  while `buzz-sandbox-firewall.service` is inactive, and the Docker runner reports
  itself unavailable.
- A sandboxed agent can have a desktop too. It runs in a second container per
  agent (`buzz-desktop-<pubkey16>`, `server/sandbox/desktop-sidecar.mjs`) with the
  same hardening and network, about 2 GB RAM, Xvnc + Xfce + Chromium +
  cua-driver. Only its `rfb.sock` (Viewport, previews) and `cua.sock` (computer
  tools, forwarded through the agent's scoped `mcp.sock`) leave the container.
  Build the image once with `server/sandbox/build-image.sh --desktop`. Guest
  tokens get it by default (`--no-sandbox-desktop`, or unticking the invite's
  "Allow a sandboxed desktop" box, turns it off). `--allow-host-desktop` still
  means a trusted, unsandboxed host-runner agent; admin tokens always have host
  desktops.

## Patched buzz-acp (no fork repo)

`patches/*.patch` sit on top of upstream block/buzz. `./build-acp.sh` (from the laptop) fetches
upstream on the server, applies them, builds `buzz-acp` in a capped `rust:<toolchain>` Docker
container and installs it (previous binary kept as `buzz-acp.prev`, version in `buzz-acp.version`).
If a patch stops applying, it says which one and installs nothing. Then restart agents:
`ssh omarchy "systemctl --user restart 'buzz-agent@*'"`.

1. Solo chats (`buzz.solo` label) are one top-level conversation under thread policy.
2. A newly joined channel replays from 60 s before the membership notification (first message isn't missed).
3. `$BUZZ_ACP_FRESH_SESSION_DIR/<channel>[_<root>]` makes that scope's next turn start a fresh session.

4. Attention wake files start turns (see Attention).
5. `session/new` names its conversation in `_meta.buzzHost` (`channelId`, `rootEventId`), so
   `acp-proxy` can start the session in that chat's workspace folder (see Workspaces). It removes
   the key before the adapter sees it.
6. `session/prompt` names its conversation and the Buzz events it answers (`id`, `pubkey`, `kind`,
   `content`, `tags`) in `_meta.buzzHost`. `acp-proxy` reads owner commands and composer picks
   only from these, never from prompt text (message content could imitate an event block), and
   removes the key.

Build on the commit already running to change only the patches: `./build-acp.sh omarchy <base>`
(`<base>` from `~/.local/lib/buzz-host/bin/buzz-acp.version`).

With the patched binary installed, agent-run sets `BUZZ_ACP_SESSION_POLICY=thread` (sessions per
thread in channels, one per Solo chat/DM, like Buzz's own agents).

## Activity

agent-run sets `BUZZ_ACP_RELAY_OBSERVER=true`: buzz-acp publishes each turn's steps and tool
calls as owner-encrypted kind-24200 observer frames, which Buzz renders as the activity bubble
under the triggering message, as it does for local agents. Turning it off leaves only typing.
The plugin's Activity tab rebuilds turns (request, tool steps, reply text, outcome) from the same
records (`session.agentActivity`, via `ctx.reflect.get("relay")`). Frames are ephemeral, so the tab
shows only what arrived while Buzz was connected.

`~/.bashrc` and `~/.bash_profile` put `agent-bin` first when `BUZZ_HOST_AGENT` is set

## Hermes agents

`hermes-acp` only views a session: the model and its tools run in the owner's shared Hermes
gateway (`hermes-gateway.service`), so nothing `agent-run` exports reaches a Hermes agent's
terminal. Instead:

- `hermes-plugin/buzz-host-session-env` sets `BUZZHOST_AGENT` for a session whose cwd is
  `~/buzz-agents/<pubkey>`, and unsets it for every other session. `deploy.sh` keeps a copy in
  `~/.local/lib/buzz-host/hermes-plugin/` and refreshes it in every profile that has it; buzz-host
  installs and enables it (`hermes -p <profile> plugins enable`) in each profile an agent runs on.
- A `buzz` function in `~/.bash_profile`, which Hermes's login-shell snapshot carries into every
  command, runs `agent-bin/buzz` when `BUZZHOST_AGENT` (or `BUZZ_HOST_AGENT`) is set.

**Profiles.** A Hermes agent runs on one Hermes profile, picked in the plugin (create form and
Settings) from `hermes profile list`, as Buzz's own Hermes plugin does. buzz-host sets
`HERMES_HOME=~/.hermes/profiles/<name>` in its `runtime.env` (none for the default profile), so its
sessions, `SOUL.md`, skills, Hermes memory and config are that profile's; the model list is the
profile's too. Changing the profile restarts the agent; Buzz's own core memory (on the relay)
stays with the agent. Under the multiplexed gateway a named profile reads provider keys only from
its own `.env`: give it the key (`hermes -p <name> config set OPENCODE_GO_API_KEY …`), or its turns
fail as "Couldn't finish" (the reason is in `~/.hermes/profiles/<name>/logs/errors.log`).

After changing the plugin: `systemctl --user reload hermes-gateway` while it is idle
(`active_agents` 0 in `~/.hermes/gateway_state.json`). Backups: `~/.hermes/config.yaml.bak-buzz-host-*`,
`~/.bash_profile.bak-buzz-host-fn-*`.

## Operating

- Run and inspect it with the [`buzz-host` command](#the-buzz-host-command) (`status`, `logs`, `doctor`, `restart`…)
- Deploy changes: `./deploy.sh`
- Call the API: `node tools/call.mjs list` / `logs '{"pubkey":"…"}'`
- Remote files: `fs.list`, `fs.read`, `fs.write`, `fs.mkdir`, `fs.rename` and `fs.delete`
  back Buzz Desktop's remote folder picker, file preview and editor; `hello` reports
  `capabilities.fs` and `capabilities.fsWrite`. Admin sessions work in this host's home.
  A guest token is jailed to its own `~/buzz-sandboxes/<tokenId>/`, shown to it as
  `/workspace` (no host path ever appears in replies or errors).
- Guest sandbox home: a guest's sandboxed agents that answer only their owner
  (`respondTo: owner-only`) share that same `~/buzz-sandboxes/<tokenId>/` as their
  `/workspace` (and their sidecar desktop's `/workspace`, linked as `~/Workspace`), so the
  guest and all their private agents work on one "computer". An agent that answers anyone
  else (`allowlist`/`anyone`), and every admin-created agent, keeps its own
  `~/buzz-agents/<pubkey>`. Chat workspace folders (`/workspace <path>` and Canvas folders)
  work inside the sandbox too, limited to `/workspace`.
- Agent logs on the server: `buzz-host logs [agent]`, i.e. `journalctl --user -u buzz-agent@<pubkey>` (macOS:
  `~/Library/Logs/buzz-host/agent-<pubkey>.log`, server in `server.log` there)
- macOS hosts: `./deploy.sh --local` installs the `com.buzz-host.server`
  LaunchAgent instead of systemd units. Sockets live under `/tmp/bh-<uid>`
  (exported as `XDG_RUNTIME_DIR`) to stay under macOS's 104-byte socket path
  limit. Agent desktops are Linux-only; `hello` reports `platform` and
  `capabilities.desktop` so clients can hide them.
  LaunchAgents live in the logged-in user's `gui/<uid>` domain, so the Mac
  needs that user logged in (automatic login on a headless Mac); logging out
  stops buzz-host and its agents. launchd respawns an agent after any non-zero
  exit (including agent-run's exit 78 for a not-yet-activated agent, every
  10 s) and leaves a clean exit down. Agent logs are not rotated.

## Attention

Buzz's Attention for remote agents: Interests (ongoing responsibilities with saved
instructions), timers and event watches that wake the agent while the laptop is off.
Off by default; the plugin's **Attention** tab turns it on per agent (restarts it). The tab
renders Buzz's own Attention markup and classes (buzz.watching's Interest cards, status menus,
Triggers/Sources/Responds in/Status table, the Sources popover, Watch details, per-watch Activity,
delete dialogs, sonar), so it looks like a local agent's; buzz-host adds the switch and "Recent wakes on
your server". Instructions render as Buzz renders them: Buzz's Markdown parser (react-markdown's
remark-parse plus remark-gfm), bundled into `plugin/src/generated/markdown-parser.js` by `plugin/build-markdown.mjs`
(rerun it after a Buzz update, then run `node plugin/build.mjs`), and Buzz's Markdown stylesheet, whose hashed class names the plugin
reads from the loaded CSS. `node --test plugin/` checks the output against react-markdown from a
buzz-app checkout. A person link (`nostr:npub…`) shows as their name: Buzz gives an agent type's
tabs no way to open a profile.

- **Same code as Buzz.** `attention/build-core.mjs` bundles buzz-app's own Attention
  format, validation, object contract, the 12 tools, the wake prompts and the catch-up
  windows into `server/attention-core.mjs` (pinned commit in its header). Rerun it after a
  Buzz update; `node --test --test-concurrency=1 attention/` tests the service against the
  bundle (catch-up against a fake relay).
- **Tools.** `runtime.env` sets `BUZZ_ACP_MCP_COMMAND` to the agent's `mcp/buzz` wrapper →
  `bin/buzz-mcp-bridge`, the compiled C stdio bridge (with `--attention` while Attention is on)
  → `$XDG_RUNTIME_DIR/buzz-host/mcp.sock`, buzz-host's shared MCP session server
  (`server/mcp-server.mjs`): one server for every session, and ~1.8 MB per session instead of a
  Node process's ~65 MB. Without the compiled bridge (no C compiler at deploy time) the wrapper
  falls back to `buzz-mcp.mjs`, the standalone server that talks to `attention.sock` (the service
  owns each agent's `attention.json`). The server is named `buzz`, as Buzz's own, so tools appear
  as `mcp__buzz__watch_add` (Hermes: `editor_buzz_*`); memory tools are always there.
- **Wakes.** Timers (Buzz's schedule, one wake per Interest at a time) and event watches
  write a request into the agent's `wake/`; patch 0004 makes buzz-acp run it in that chat
  or thread's session, or as an independent turn, and write `wake/results/<id>.json`.
  A spent timer is removed after its last wake succeeds.
- **Event watches.** `attention-relay.mjs` keeps one connection per agent with live event
  watches, logged in as the agent (NIP-42 + NIP-OA), subscribed to just their channels and kinds.
- **Catch-up (Buzz's).** Each watch × channel has a checkpoint in `attention.json`. On every
  (re)connect, including a buzz-host restart, a watch reads what it missed up to the connect
  (`until`/`before_id` pages, newest first, at most 256×16 events / 8 MB; older ones are skipped and
  the wake says so) and gets it oldest first in catch-up wakes of at most 64 events / 64 KB. Live
  events wait behind it. Channels live does not cover (public channels the agent has not joined,
  for `channels: "all"`) are polled every 30 s, ~10 s behind. Events heard live are listed in the
  checkpoint, so nothing is delivered twice; a batch's checkpoint is saved before it is delivered,
  so a crash can lose a batch, never repeat it. While Attention is off, an Interest paused or a watch
  off, its checkpoints move to now: nothing is replayed when it comes back.
- **Queue and limits (Buzz's).** Watch work waits per agent (32 jobs, 8 per Interest); one wake at a
  time per Interest, at most 8 Interests at once, at most 60 admitted per minute. Live work past
  that is dropped and shown as "dropped (busy)"; catch-up waits for room. The queue is in memory.
- **Review note.** `attention-note.txt` holds Buzz's end-of-turn review; `acp-proxy` adds it to every turn.
- **Not yet (phase 3):** classifiers (saved, reported unavailable, events pass unchecked),
  source watches (saved, never run).

## Memory

Buzz's agent memory for remote agents (2026-11-17), so the owner sees it in the agent's
**Memory** tab in Buzz, which reads it from the relay for any agent.

- **Tools.** `mem_get`, `mem_set`, `mem_rm`, Buzz's names, descriptions, version checks and
  replies (`server/memory.mjs`, ported from buzz-app `src/buzz-mcp/tools.ts`), served by the
  `buzz` MCP server whether or not Attention is on. `mem_set`'s `path` is read inside
  the session's folder: by the shared `mcp.sock` server behind the C bridge, or by
  `buzz-mcp.mjs` when that is the fallback.
- **Format.** Kind 30174 from the agent, tags exactly `d` + `p` (owner); `d` is the HMAC of
  `agent-memory/v1/d-tag\0<slug>` under the agent↔owner NIP-44 conversation key; content is
  NIP-44 v2 of `{slug, value}` (`{slug, profile}` for `core`; `value: null` deletes). NIP-44 is
  buzz-app's nostr-tools, bundled by `memory/build-nip44.mjs` into `server/nip44.mjs`.
  Reads/writes go through the relay's HTTP API as the agent (NIP-98 + its NIP-OA tag).
- **Core.** acp-proxy adds Buzz's "Agent Memory" guide and `<core-memory>` to the first turn
  of each session it sees (Buzz puts both in a local agent's prompt at process start).
- **Tests.** `node --test memory/` (format, owner-side decryption, versions, the core note).
- Existing agents were moved from `mcp/attention` to `mcp/buzz` once by buzz-host at startup.

## Native look in Buzz

With the owner's Buzz patched (`~/Work/buzz-pkg/patches/0004-agent-ui-for-plugins.patch`), Buzz
provides its own setting components to plugins (`ctx.reflect.get("agentUi")`). The plugin builds
from them:

- the New agent fields: Harness, Runtime, Hermes profile and Model rows, then Instructions;
- the agent's **Identity** tab: Harness, Runtime, Hermes profile and Model rows, Instructions, and
  Buzz's save bar;
- its **Settings** tab: Server, Sessions, Restart and Logs rows, then Buzz's agent details.

The Model menu is Buzz's `ModelPicker`, with Hermes models grouped by provider. On an unpatched
Buzz the plugin falls back to its own plain controls. Patch 0002 likewise gives the Activity tab
Buzz's own panel.

**Attention tab:** patch 0005 provides Buzz's own Attention tab
(`ctx.reflect.get("attentionTab").create(source, setting)`). The **Hive Watch** plugin (`plugins/hive-watch/`) feeds it from buzz-host and registers a dedicated **Attention** tab on self-hosted agents:

- `attention.view` returns the agent's record in Buzz's shape (`attention`, `skipped`, `timers`,
  `attentionHistory`).
- `attention.change` applies the tab's edits as Buzz's own `changed()` does: an
  `attentionExpected` check, Interest pause and delete, and watch on/off.
- `setting` puts the plugin's on/off switch and "Runs on your server" into Buzz's Attention row.
- buzz-host now keeps Buzz's per-watch `attentionHistory`: `lastWokeAt` plus the last 10
  waking events or timer prompts.
- "Recent wakes on your server" stays below the tab.

## Model, effort and session controls in the composer

With Buzz patch `0006-models-for-hosted.patch`, a hosted type may offer `models` and
`sessionControls`, so the composer's gauge button works for self-hosted agents as for local ones:

- **Catalog:** the plugin's `models(agent, place)` calls buzz-host `catalog` (with `channelId` and
  `threadRootId` when Buzz passes `place`). buzz-host (`server/catalog.mjs`) opens one unprompted
  ACP session per runtime / Hermes profile, sets each model in turn and reads its effort levels
  (Hermes: one set for all models, so no walk). A model the runtime refuses ("Usage credits are
  required") is left out. Cached 6 h in `~/.local/share/buzz-host/catalog/`, refreshed in the
  background; the plugin caches per conversation and invalidates when `session.state` reports that
  the chat's runtime, model, or effort changed in `chat-settings.json`. Hermes models carry `group`
  = provider; Buzz lists each provider as a submenu.
- **Picks:** Buzz puts `["model"|"effort", <agent>, value]` tags on the owner's message.
  `acp-proxy` applies the latest owner message's picks to that turn only (ahead of `/model`,
  `/effort`); the next turn without one goes back to the chat setting, else to what the session ran
  before (`model-restore.json` in the agent dir keeps that across restarts). In a Solo chat Buzz
  resends the chat's pick with every message until it's reset.
- **Session buttons:** `sessionControls` state comes from buzz-host `session.state` (the plugin
  polls every 2–5 s while Buzz reads it); `session.control` maps Compact to the session's own
  `/compact` (Claude, Codex, Antigravity) or `/compress` (Hermes) run as acp-proxy's turn (buzz-acp never sees
  it; its next prompt waits), New session to `/new`, Interrupt to the Stop path. `catalog`,
  `session.*` and `interrupt` skip buzz-host's per-agent call queue.
- On stock Buzz the type refuses `models`; the plugin then registers without them.

## Workspaces

A chat's workspace is the folders it works in, as Buzz's Solo **Workspaces** give them to local
agents. Where they come from, first match wins:

1. `@agent /workspace <path>...` (owner only; per chat or thread, a thread inherits its channel's).
   `/workspace` shows it, `/workspace off` means none (Canvas folders ignored), `/workspace default`
   goes back to the Canvas. Every path must exist on the server, or nothing changes.
2. The chat's Canvas: Buzz writes a workspace's **Folders** (and worktree mode) into each new Solo
   chat's Canvas as a `buzz-session-workspace:v1` block. `workspace.mjs` reads the newest revision as
   the agent and uses it only as Buzz does: written by the owner, or by an agent whose NIP-OA `auth`
   tag the owner signed, with no `canvas-instructions` tag, and a valid event signature.

Paths are on this server: `~` is its home. A laptop path (`/home/<user>/x`, `/Users/<user>/x`) that is
missing here maps to `~/x` when that exists, so a workspace made with Buzz's folder picker works when
the server keeps the same layout under its home.

- **Claude, Codex and Antigravity** start each new session in the chat's first folder found here, so its
  `CLAUDE.md`, `.mcp.json`, skills and settings load. Claude and Antigravity also get the chat's other folders, the
  worktree location and the agent's own workspace as ACP `additionalDirectories`. This goes further
  than Buzz does for local agents (it names the folders but starts in the agent's workspace).
  A session keeps its folder: `/workspace` asks for a fresh session; a Canvas change applies to the
  chat's next new session (`/new`).
- **Hermes** keeps the agent's own folder (the session cwd is how its gateway plugin knows which agent
  it is) and gets the note below.
- **Every turn** of a chat with a workspace gets Buzz's `<workspace-canvas>` note: the folders, where
  the session started, folders not found on the server, and for a Canvas workspace the Canvas itself
  (re-read at most every 15 s). When a chat's workspace goes away, one turn says to disregard it.

Tests: `python3 -m unittest discover -s server -p 'test_*.py'` (acp-proxy) and `node --test server/`
(`workspace.mjs`, including signed and attested Canvases).

## Agent desktops

An agent the owner gives a desktop (agent → Settings → Desktop switch; meta `desktop: true`,
off by default) gets its own headless Linux desktop on the server and the **computer tools** in its
`buzz` MCP server (`buzz-mcp.mjs --computer`): cua-driver's MCP tools (screenshot, click, type,
browser…, about 65), served through `desktop/computer.mjs`.

- **Desktop:** TigerVNC `Xvnc` + a minimal Xfce, started by Hermes Bot Desktop's `launcher.sh`
  on a free display (`:90`–`:189`) on first use, plus a cua-driver daemon bound to that display.
  State in `agents/<pubkey>/desktop/`; sockets in `$XDG_RUNTIME_DIR/buzz-host/desktop/<pubkey[:16]>/`
  (a socket path is capped at 107 bytes). Its own browser profile (`desktop/bin/browser`,
  `--password-store=basic`) is the desktop's default for links.
- **Never the owner's screen:** the launcher and driver get an allowlisted env (no `WAYLAND_DISPLAY`,
  Hyprland variables or agent keys: an inherited `WAYLAND_DISPLAY` makes cua-driver drive the real
  Hyprland cursor), and the driver runs in `bwrap` with a minimal `/dev`, because cua-driver ≥ 0.28
  injects X11 input through `/dev/uinput`, which the owner's session would also receive.
- **Driver:** cua-driver 0.55 in `~/.local/share/buzz-host/tools/cua-driver-0.55.0-linux-x64/`
  (`BUZZHOST_CUA_DRIVER` overrides). Its tool list is cached per version in the desktop folder, so
  listing tools never starts a desktop. Needs `tigervnc`, `xfce4-panel`, `xfwm4`, `xfdesktop`,
  `xfce4-settings`, `bubblewrap` and a Chromium on the server.
- **Watching and taking over:** a full-screen view with noVNC (bundled into `plugin/src/generated/novnc-client.js` by
  `plugin/build-novnc.mjs` and inlined into `plugin/plugin.js` by `plugin/build.mjs`) over `wss://…/desktop?ticket=…` (same Tailscale login and Origin checks;
  `desktop.view` issues a single-use 60 s ticket and the viewer id that connection takes over with).
  **Take over** (`desktop.lease`) makes the agent's computer tools refuse every call, screenshots
  included; the bridge forwards keyboard, mouse, clipboard and resize only from the viewer holding
  control. **Hand back**, or closing the view, returns control. The lease file fails closed.
- **Where:** the **Viewport** plugin (`plugins/viewport/`) registers a dedicated **Desktop** tab on self-hosted agents (on/off switch, which restarts the agent;
  **Open desktop**; **Stop desktop** while it runs), alongside the in-chat preview
  during a turn. Both open the same full-screen view (the plugin's `desktopViewer`): an overlay on
  `document.body`, refitted after it is placed (noVNC rescaled, back buffer redrawn: WebKitGTK
  otherwise shows a newly placed canvas black until the next frame). Closing it closes the view.
  Buzz's webview takes the Esc key to leave monitor-wide full screen, so the toolbar has an **Esc**
  button that sends it to the agent's desktop.
- **In-chat preview:** under the activity bubble of a request the agent is working on, once that
  turn has used a computer tool, a still of its screen every ~1.5 s with **Take over** and **Stop**;
  a click opens it full screen, watching. After the turn it stays as the last screen. It is a plain
  `ctx.conversation.registerAccessory({ placement: "response" })`, so it needs no Buzz patch. The
  turn and its chat come from Buzz's activity; `acp-proxy` labels each session's `buzz` MCP server
  with `BUZZHOST_CHAT`, and `computer.mjs` records each admitted computer-tool call per chat in
  `desktop/activity.json` (`lastUse` / `byChat`), so the card shows only in the chat using the computer.
  Stills come from `desktop/snapshot.mjs` (one shared Raw RFB frame from `rfb.sock`, box-filtered,
  PNG) through buzz-host's API over Tailscale, never the relay. Sessions started before this change
  record nothing until they restart (`@agent /new`).
- API: `desktop.status` (with `lastUse`), `desktop.set {enabled}` (restarts the agent), `desktop.start`,
  `desktop.stop`, `desktop.view`, `desktop.lease {viewer, take}`, `desktop.snapshot {width, since, etag, channelId, threadRootId}`
  (never starts the desktop; no picture without computer use in that chat since `since`, or when `etag` matches).
  Removing the agent stops its desktop.
- Tests: `node --test server/desktop/` (lease, RFB filter, snapshot and per-chat activity).

## Install on a new machine (bundle)

Release bundles set up a machine with one command: no checkout, no `deploy.sh` run by hand, no
Docker build of buzz-acp on the target.

```sh
curl -fsSL https://github.com/ytheesh96/buzz-host/releases/latest/download/install.sh | sh -s -- --up
```

The repo is private, so for now plain `curl` can't fetch Release assets. Use one of these instead:

- With `GH_TOKEN` set, or an authenticated `gh`, install.sh fetches the assets itself:
  `gh release download -R ytheesh96/buzz-host -p install.sh && sh install.sh --up`
- Copy a bundle over and run `sh install.sh --bundle buzz-host-linux-arm64.tar.gz --up`. The
  checksum comes from `<file>.sha256` or `SHA256SUMS` next to the file, or from `--sha256`.

What the pieces do:

- **Bundles** (`.github/workflows/release.yml`, on a `v*` tag): one `buzz-host-<target>.tar.gz`
  per target (`linux-x64`, `linux-arm64`, `darwin-arm64`), plus `SHA256SUMS` and `install.sh`,
  attached to the GitHub Release.
  - Each bundle holds the files `deploy.sh --local` installs (`deploy.sh`, `server/`,
    `hermes-plugin/`, `agy-plugin/`, minus tests), the `buzz-host` CLI (`bin/`, `cli/`) and a
    pinned Node (`node/`, version and checksums in `bundle/node.env`).
  - It also holds prebuilt `bin/buzz-acp`, `bin/buzz` (upstream block/buzz at
    `bundle/UPSTREAM_REF` plus `patches/*.patch`), `bin/buzz-host-iroh` and
    `bin/buzz-mcp-bridge`.
  - Linux binaries are built on Debian 12 (glibc 2.36).
  - To build one locally: `bundle/build-upstream.sh <bins>`, then
    `bundle/make-bundle.sh --version … --target … --bins <bins> --out <dir>`.
- **install.sh** checks the tarball and unpacks it into
  `~/.local/share/buzz-host/runtime/<version>`. It then points `runtime/current` at that version,
  keeps the version it replaced and deletes older ones, and links `~/.local/bin/buzz-host`.
  - It needs only `curl` or `wget`, `tar` and `sha256sum` or `shasum`.
  - `--up [args…]` runs `buzz-host up [args…]` afterwards.
- **`buzz-host up`** is safe to re-run. It does these steps in order:
  1. Writes `~/.config/buzz-host/config.json` if it's missing. A new config is token-only:
     `guestPort` 8467, no `allowLogins`, and an empty `publicGuestUrl` so the host doesn't
     advertise omarchy's URL. An existing config is kept; up only adds a missing `guestPort` and
     what the flags below set.
  2. Runs the bundle's `deploy.sh --local` without restarting anything, with
     `BUZZ_HOST_NODE=<runtime>/current/node/bin/node`. It then copies the prebuilt binaries
     whose bytes changed, keeping the old buzz-acp as `buzz-acp.prev`, and links `bin/node` to
     the bundle's Node.
  3. npm-installs the Claude and Codex ACP adapters if they're missing (`--no-adapters` skips
     this).
  4. Linux: enables lingering, runs `daemon-reload`, enables `buzz-host.service` and restarts
     it. macOS: (re)bootstraps the `com.buzz-host.server` LaunchAgent. Either way, buzz-host
     restarts only when files or config changed, then up waits for `/health`.
  5. Prints the connection info.

  Re-running up with the same bundle restarts nothing. A new bundle upgrades in place and
  restarts buzz-host. Agent units (`buzz-agent@<pubkey>.service`) are never touched, so agents
  keep running and pick up a new buzz-acp at their next restart. `--no-service` installs only
  the files and config. `buzz-host up --help` lists every flag. Reaching the machine:
  - **Same machine:** Buzz Desktop accepts `ws://127.0.0.1:<guestPort>` (and `localhost`/`[::1]`)
    directly. Every other host must be `wss://`.
  - **`--tailscale-serve [--tailscale-path /_buzz-host]`:** checks that Tailscale is logged in
    with a MagicDNS `*.ts.net` name and HTTPS certificates. It then runs
    `tailscale serve --bg --set-path <path> http://127.0.0.1:<guestPort>` and saves
    `wss://<name>.ts.net<path>` as `publicGuestUrl`. buzz-host stays bound to loopback; only your
    tailnet can reach the URL. Each failure names its fix (`tailscale up`, enable MagicDNS/HTTPS in
    the admin console, `sudo tailscale set --operator=$USER`).
  - **`--lan` / `--no-lan`:** binds the token listener to `0.0.0.0`, or back to `127.0.0.1`
    (saved as `guestHost`). Every socket still needs an access token. On a LAN socket
    `X-Forwarded-For` is ignored (only a loopback tunnel may set it). Buzz Desktop needs `wss://`
    for other machines, so put TLS in front of it.
  - **Discovery with no agents yet:** `--owner <npub|hex> --relay wss://…` saves `ownerPubkey` and
    `discoveryRelays`. Buzz only trusts a status event signed by a key its owner attested, so
    buzz-host has its own machine key (`~/.local/share/buzz-host/machine-key`, 0600). `pair`
    prints that key. Authorize it in Buzz (Settings → Security), then pass the proof with
    `--owner-proof '["auth",…]'`; up saves it as `ownerAuth`. From then on the machine key
    publishes to each such relay that none of the owner's agents already covers. Over an admin
    connection, the app can do the same with the `machine.attest {auth, relay}` RPC; `hello`
    gives admins `machinePubkey` and `discoveryOwner`.
- Host requirements: `bash`, `python3` (acp-proxy), systemd with a user manager (Linux) or a
  logged-in user (macOS). Optional: a C compiler (otherwise the prebuilt MCP bridge is used),
  Docker (sandboxed agents) and Tailscale (Funnel/Serve URLs).
- omarchy keeps deploying from git (`deploy.sh`, auto-deploy). Without `BUZZ_HOST_NODE`,
  `deploy.sh` behaves exactly as before.

### `buzz-host up --json` (stable contract)

`buzz-host up --json` prints exactly one JSON object on stdout. Logs go to stderr. The exit code
is 0 on success and non-zero on error, with the message on stderr. The Buzz app's SSH machines
(#46) read this object:

```json
{"version":"0.1.0","url":"ws://127.0.0.1:8467","token":"bha_…","pubkey":"5daa…02d8"}
```

| Field | Always | Meaning |
|---|---|---|
| `version` | yes | Bundle version (`VERSION`; `dev` in a git checkout) |
| `url` | yes | Where clients connect: the config's `publicGuestUrl` (or `--url`) if set, else `ws://127.0.0.1:<guestPort>`, local to the host and meant to be reached through an SSH tunnel |
| `token` | yes | An admin access token (`bha_…`) for the token listener (send it in the first `auth` call). Re-runs print the same token while it's live. It's kept in `~/.config/buzz-host/up-token.json` (0600). Revoke it with `buzz-host tokens revoke <id>` and the next `up` mints a new one |
| `pubkey` | no | The machine's iroh endpoint id, present once `buzz-host-iroh` is up |

New fields may be added later. These four keep their names and meanings.

### The `buzz-host` command

One command for day-to-day running, the same on systemd (`--user`) and launchd. In a bundle install
it's `~/.local/bin/buzz-host`; in a checkout, `bin/buzz-host`. Every subcommand takes `--help`, and
`--json` prints one JSON document on stdout (errors go to stderr, exit 1; a mistyped command line
exits 2).

| Command | What it does |
|---|---|
| `up` | Install/upgrade and start (above). Its `--json` contract is unchanged |
| `status [--json]` | buzz-host's and every agent's unit state (`active`, `inactive`, `failed`…), listener `/health`, URL, iroh node id, discovery, version. Exit 0 when buzz-host is running, 3 when it isn't |
| `down [agent] [--keep-agents]` | Stop buzz-host and all agents, or just one agent. Units stay installed: they start at the next login, `up` restarts buzz-host, `restart --agents` starts the agents |
| `restart [agent] [--agents]` | Restart buzz-host and wait for `/health`; agents keep running unless `--agents`, or name one. Also starts a stopped unit |
| `pair [--new] [--label …] [--url wss://…] [--qr]` | URL, admin token, the 1-paste pairing URL and a `buzz://pair?url=…&name=…#token=…` link (`deepLink` in `--json`) that opens Buzz Desktop's Add machine form prefilled for you to confirm. Also the iroh node id, routes, discovery relays and the machine key / owner attestation state (PR #38). Prints the token `up` does (made if missing); `--new` mints a separate admin token for one device. `--qr` draws a QR code with `qrencode` when it's installed |
| `tokens create \| create-admin \| list \| revoke` | The access-token commands, as in `buzz-host-tokens` |
| `logs [agent] [-n 80] [-f]` | buzz-host's log, or one agent's: `journalctl --user` on Linux, `~/Library/Logs/buzz-host` on macOS |
| `doctor` | Read-only checks: user service manager and linger, installed files, config, buzz-host and its ports, iroh, runtimes installed and signed in (Claude, Codex, Hermes, Antigravity), Python, Docker, tokens. Prints a fix for each problem; exit 1 if a check fails |

An `agent` is a name (case-insensitive) or a pubkey prefix of 4+ hex digits. `status --json` looks like:

```json
{"version":"0.1.0","bundleId":"…","platform":"linux","url":"wss://…",
 "server":{"unit":"buzz-host.service","state":"active","listeners":[{"role":"token","port":8467,"healthy":true}]},
 "iroh":{"nodeId":"…"},
 "discovery":{"enabled":true,"relays":["wss://…"],"machinePubkey":"…","owner":{"pubkey":"…","relays":["wss://…"],"attested":true}},
 "agents":[{"pubkey":"…","name":"…","runtime":"claude","runner":"host","unit":"buzz-agent@….service","state":"active"}]}
```

Tests: `node --test cli/` (`cli/manage.test.mjs` covers each subcommand on both platforms against a
temporary HOME with fake `systemctl`/`launchctl`).

## Deploying & Auto-deploy

- **Manual deploy:** `./deploy.sh [host]` (default `omarchy`, over SSH) or `./deploy.sh --local` directly on the server (atomic temp-file + `mv` installs, preserving unmanaged binaries like `bin/buzz-acp` and `npm/`).
- **Pull-based auto-deploy on merge (`buzz-host-deploy.timer`):**
  - Enable once on the server: `./server/enable-auto-deploy.sh --seed` (or without `--seed` to deploy immediately).
  - Every 2 minutes `server/auto-deploy.sh` fetches `origin/main` into a dedicated clean checkout (`~/.local/share/buzz-host-deploy/repo`, separate from `~/Work/buzz-host`), skips restarting if no files under `server/`, `hermes-plugin/`, or `deploy.sh` changed, runs the local server test suites, snapshots managed files, installs atomically via `deploy.sh --local`, restarts `buzz-host.service`, and verifies `is-active` + `http://127.0.0.1:<port>/health` — rolling back automatically on failure.
  - Trigger on demand: `systemctl --user start buzz-host-deploy.service`; inspect logs with `journalctl --user -u buzz-host-deploy.service`.

## Limits

- Buzz's own Attention doesn't run remote agents; buzz-host's does (above), without classifiers or source watches yet.
- Buzz's composer picker and session buttons need the owner's patched Buzz (patch 0006, see above); the chat commands (`@agent /help`) still work everywhere, the phone included.
- Saving instructions or runtime restarts the agent, as does turning its desktop on or off.
- Runtimes use the server's own sign-ins: `claude` login, `codex login` (ChatGPT) or
  an API key, `hermes model`, and `~/.local/share/mise/shims/agy acp --login` for Antigravity.
